# Этап 6. Сборка скелета на VPS

Статус — выбран, рекомендации на утверждении.

## Объём

Собираем один Android APK и совместимый сервер Godot 4.7.2. Сохраняем текущий игровой адрес, порт и SQLite-базу Lunex. Перед переключением проверяем новую серверную сборку с отдельной тестовой БД. Для проверки восстановления перезапускаем игровую службу и повторно входим с тех же установок Android.

Основной интерфейс объединяет вход, управление, бой, прогресс, чат и выход в существующих сценах. Добавляем отдельную редактируемую панель диагностики с кнопкой показа и сбросом замера для нового прогона.

## Что предлагаю внедрить

| Источник | Применение |
| --- | --- |
| [Godot Performance 4.7.2](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/Performance.xml) и [ENetPacketPeer 4.7.2](https://github.com/godotengine/godot/blob/4.7.2-stable/modules/enet/doc_classes/ENetPacketPeer.xml), Godot MIT | Используем встроенные счётчики для FPS и длительности кадра, а ENet — для задержки до сервера. На VPS измеряем загрузку CPU и RSS игрового процесса средствами Linux и собираем длительность серверного физического тика и число игроков из Godot. В отчёте указываем условия и продолжительность замера. |
| [Perfetto](https://github.com/google/perfetto), Apache 2.0 | Оставляем инструментом дополнительной диагностики Android при заметных просадках. Для первого прогона достаточно панели внутри игры, которая работает без подключения телефона к ПК. |
| [sysstat](https://github.com/sysstat/sysstat), GPL-2.0 | Проверили `pidstat` как внешний вариант для CPU и RSS. Для короткого прогона используем данные Linux по PID службы, поэтому устанавливать пакет на VPS не нужно. |

## Итоговый прогон

1. Два Android-устройства запускают одну версию APK и входят в зону под разными профилями. В отчёте фиксируем версию сборки, модель устройств и тип подключения.
2. Игроки видят движение друг друга и обмениваются сообщениями. В совместном бою один использует автоигру, второй попадает вручную. Каждый с активным заданием получает награду и экипирует кольцо.
3. Сохраняем замеры во время игры. Перезапускаем игровую службу, проверяем её журнал и порт. На обоих устройствах повторно входим и сверяем задание, опыт и экипировку.
4. Записываем результаты сценария и показатели Android и VPS в репозитории. Результаты двухклиентского прогона описывают текущий скелет. Нагрузочные цели для MMO определим после замеров.
