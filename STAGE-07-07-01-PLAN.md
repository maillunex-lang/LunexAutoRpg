# 7.7.1 — технический план, без реализации

**Цель:** заложить модель класса и безопасное сохранение, не меняя текущую боевую логику.

## Предлагаемый объём
1. Перед работой снять контрольные суммы и копии тестовых SQLite, зафиксировать схему и baseline: 7.5 20/20, 7.6 15/15, SQLite 26/26. Не трогать production DB.
2. Спроектировать `LunexClassDefinition` (Resource) с неизменным `class_id`, названием, ролью, базовыми атрибутами, иконкой, ссылками на способности. Четыре `.tres` в отдельных файлах. Проверка уникальности идентификаторов и диапазонов.
3. Проект SQLite: расширение `profiles` столбцом `class_id TEXT NOT NULL DEFAULT ''` с проверкой `PRAGMA table_info(profiles)`; транзакционная идемпотентная миграция. Пустое значение = legacy/unassigned. Не переписывать существующие quest_progress, chapter_quests, experience, equipped. Запрет клиентского прямого SQL.
4. В `read_profile()` добавить безопасное поле `class_id`; старые клиенты/профили получают прежний формат остальных полей. На сервере проверять допустимость класса только по whitelist ресурсов.
5. Ввести отдельно вычисляемые базовые атрибуты (health, damage, attack_interval) с сохранением текущих значений для legacy. В 7.7.1 **не подключать** их к `NetworkPlayer._attack`, `take_counter_damage`, UI или PvE.
6. Написать unit/integration-тесты: чистая БД, миграция старой БД, повторная миграция, независимость двух профилей, сохранение всех квестов и экипировки, отклонение невалидного класса, повторное подключение, restart, повреждённая схема с rollback.
7. Проверить Godot 4.7.2 headless import, серверные тесты и Android экспорт **только в изолированной dev-копии**. Подготовить отчёт и дождаться приёмки 7.7.1 до 7.7.2.

## Границы и риски
- Миграция не должна назначать класс автоматически и менять боевые показатели существующих персонажей.
- Выбор класса и интерфейс относятся к 7.7.2, способности и перезарядки к 7.7.3.
- Для SQLite DDL в транзакции проверять реальные свойства godot-sqlite и версии SQLite; откат при ошибке.
- Развёртывание на production, обновление test-сервера и установка GitHub-плагинов исключены.
- Нужна отдельная приёмка поведения существующих персонажей без класса перед реализацией.

## Критерии приёмки 7.7.1
Ни одна прежняя запись не потеряна; повторная миграция не меняет данные; старые профили играют как раньше; классы представлены редактируемыми ресурсами; все регрессии зелёные; отдельный отчёт о тестах и diff; никаких изменений production.
